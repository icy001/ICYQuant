## 2. Stage D 特有治理原则

### 2.1 原则 P-1：设计评审 ≠ 实施授权（分离原则）

**原文依据**：v8 §11 第 9 条：

> "技术债与授权边界明确：……**设计评审通过不等于代码实施、Stage 02 运行、产物生成或下游数据集准入已获授权。任何后续实施须独立启动并获得相应授权。**"

**展开表**：

| 动作 | 能否由"设计评审通过"推导出授权 |
|---|---|
| 设计文档评审 | —（评审本身，非授权） |
| 代码实施 | **否** |
| Stage 02 流水线运行 | **否** |
| 产物生成 / 重建 | **否** |
| 下游数据集准入 | **否** |
| PC-5 数值批准 | **否**（须对应角色审批 + L2 记录） |
| 角色任命 | **否**（须项目授权主体作出） |

**关联历史事实**：评审记录 §2.1 确认——"Stage 02 产物先于 v2 设计文档的流程顺序"问题**保留为尚无法独立确认**，不预先写成已通过的结论。

### 2.2 原则 P-2：双层生效（L1 角色登记 + L2 批准记录）

**原文依据**：v8 §7"记录位置"第 1–3 条（line 457–459）。

| 层 | 载体 | 内容 | 权威性 |
|---|---|---|---|
| **L1** | v8 §7.x 各子节 + §7 角色表"持有人"列 | 规则内容、规则 ID 与版本、依据类型、审批角色、决策理由；角色登记状态 | 规则内容与角色指定状态的**唯一权威来源** |
| **L2** | Stage D 自有版本化契约与证据记录（**当前尚未建立**，属 PRE-IMPL PI-03） | 批准结论、批准角色持有人、规则版本、生效时间、生效范围 | **只引用**或同步 L1，**不**作登记源 |
| **生效条件** | — | 须**同时**满足 L1 登记 + L2 记录 | 未同时满足 → 规则不生效，相应门禁保持 NOT ASSESSED |

**禁令**：

- 不得写入既有 `artifacts/histdata_v9/quality_contract.yaml` 的既有条目（v8 §4.1）。
- L2 载体不得被描述为已存在，也不得作为角色持有人登记的依据（v8 §7）。
- 任何"由项目维护者指定"而未在 L1 登记的表述，均**不**构成角色已指定（v8 §7）。

**当前状态**：L2 未建立；**2026-10-15 仓主决策"暂不任命"**（见 `docs/design/histdata_stage_d_role_appointment_registry.md` §5.1）→ L1 的 8 角色均未登记 → 相关规则不生效。

### 2.3 原则 P-3：证据分级

**依据**：G6-1 报告（`a3af532f` 创建 + `668626dd` 追加裁定）与 G6-2 报告（`2bf8f9a9`）已采用的证据分级实践。

| 分级 | 定义 | 允许的表述 |
|---|---|---|
| **有证据（直接）** | 可由仓库内机器可读事实直接确认（commit / 文件 / 行号 / 时间戳 / 内容） | 可作为事实陈述 |
| **证据不足** | 存在部分证据但不足以支持结论（如仅 commit message 声明） | 只能记为"证据不足" |
| **无法独立确认** | 仓库内无可用证据，需外部来源 | 只能记为"无法独立确认" |

**强制要求**：

1. 任何事实陈述须标注**分级**与**证据来源**（文件 / 提交 / 行号）。
2. 引用必须**可定位**；无法定位的引用不得作为依据。
3. 不得以"评审通过""设计已说明""众所周知"等表述替代证据分级。
4. 历史事实的授权来源不明时，**保留为"无法独立确认"**，不得预先写成已通过结论（评审记录 §2.1）。

### 2.4 原则 P-4：历史事实裁定

**依据**：G6-1 §8 三条裁定 + 评审记录 §3、§4。

| 规则 | 内容 | 来源 |
|---|---|---|
| **不追溯否认** | 已发生的实施事实（如 v2 设计文档之前已存在的实施）**不**以"后续设计未授权"为由追溯否认 | G6-1 / G6-2 裁定；v8 §11 第 9 条"向未来不授权" |
| **既有事实承认** | 设计文档对既有验收记录的承认构成事实承认（如 v8 §11 第 2 条"现有 14 个 Acceptance ID 保持不变"） | v8 §11 第 2 条 |
| **事后封存归类** | 运行在前、commit 在后的产物入库，归类为"**既有运行产物的归档入库**"，**不**视为新增实施 | G6-2 候选 A 含义（评审记录 §4.3） |
| **不得预先定性** | 授权来源不明者**保留**"无法独立确认"，不预先写成已通过结论 | 评审记录 §2.1、§3 |

**记录方式**：历史事实裁定须**逐条登记**（编号 / 事实 / 分级 / 处置 / 依据 / 落盘状态），载体为 `docs/reviews/` 下的证据报告与评审记录；勘误须以**独立 commit** 追加（与设计修订解耦），如 `0ff6b69c`。

## 3. 治理动作与授权链

### 3.1 动作类型与授权主体

| 动作 | 授权主体 | 记录载体 | 当前状态 |
|---|---|---|---|
| 设计文档修订 | 项目授权主体（仓主） | 设计文档 commit（独立提交） | 可用 |
| 角色任命 / 登记 | 项目授权主体 | 任命登记表 + v8 §7"持有人"列 | **暂不任命**（2026-10-15） |
| 规则批准（PC-5 数值） | 对应规则审批人（DQA / TSA / CA / RSA / RPA / DAA） | L2（未建立，PI-03） | 未启动 |
| 门禁状态评审 | GA | L2（未建立） | 未启动（GA 未任命） |
| 代码实施 / 流水线运行 | **独立授权**（不得由设计评审推导） | 独立授权记录 | 未授权 |
| 产物入库 / 数据集准入 | **独立授权** | 独立授权记录 | 未授权 |
| 证据报告 / 评审记录落盘 | 项目授权主体 | `docs/reviews/` | 可用 |

### 3.2 顺序约束（不得倒置）

```
设计（含未决事项分类）
  → 设计评审（记录结论，不构成授权）
  → 独立授权（每类动作分别授权）
  → 实施 / 运行
  → 产物封存
  → 门禁评审（GA；须 L1 + L2 就位）
  → 数据集准入（DAA）
```

**禁止倒置**：

- 不得以实施结果反推设计已批准。
- 不得以设计评审通过代替实施授权。
- 不得以文字修订代替实际验收（评审记录 §8 顺序约束；v8 §11 程序性说明）。
- P0 必决事项不得以延期方式绕过退出条件（v8 §11）。

## 5. 门禁状态治理（四态）

| 状态 | 定义 | 依据 |
|---|---|---|
| **PASS** | 所有必需 PASS 条件成立且无禁止情形 | v8 §6.2.3 第 4 条 |
| **FAIL** | 已枚举的硬性规则被违反 | 同上 |
| **PASS-W** | 必需 PASS 条件成立且限制落入 §6.5 允许列 | v8 §6.5 |
| **NOT ASSESSED** | 证据不足 **或** 规则未批 | v8 §6.1 / §6.3 |

**判定顺序**（v8 §6.2.3 第 4 条）：① 检查是否有已枚举硬性规则被违反（是 → FAIL）→ ② 检查必需 PASS 条件是否全部成立（否 → NOT ASSESSED）→ ③ 检查是否存在 §6.5 允许列的限制（是 → PASS-W）→ ④ 否则 PASS。

**NOT ASSESSED 两成因**（证据不足 / 规则未批）须**逐项区分**并显式注明，不得一笔带过（v8 line 358）。

**当前状态**：D-G01 至 D-G07 **全部 NOT ASSESSED**（GA 未任命 + 规则未批 + L2 未建立）。
