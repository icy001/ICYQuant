## 1. 目标、范围与非目标

### 1.1 目标

Stage D 是位于既有 Stage 01（M1 解析）与 Stage 02（M1→D1
派生）之上的独立历史数据可信度与研究准入验证层。其目标是：

1.  明确原始时间戳的源时区语义，并定义可审计的规范 UTC 时间轴。
2.  验证 M1→D1 的日期归属、OHLCV 聚合、输入输出对应关系与异常处理。
3.  建立异常样本、解析错误、派生数据及验证报告之间的可追溯证据链。
4.  验证在固定输入、规则版本和环境条件下，派生产物是否可重复生成。
5.  为下游研究给出有边界的数据集状态、适用范围和明确限制。

### 1.2 范围内

-   HistData EURUSD 历史 M1 数据及其 D1 派生产物。
-   原始输入清单、源文件身份、覆盖范围、时间戳语义与解析错误追踪。
-   Stage 02 的 D1 重采样、spike quarantine、EDA 报告及派生产物契约。
-   质量门禁 D-G01 至 D-G07、证据要求、状态和下游准入结论。
-   设计迁移、版本标识、兼容性和回滚原则。

Stage 02 在 Phase 0 中仅作为设计参考对象，不作为实施对象。本阶段对 Stage 02 的分析仅用于确认当前实现行为、识别契约缺口和制定 Stage D 的独立验证要求，不授权修改 Stage 02 代码、运行其流水线、重建其产物或改变既有验收记录。Stage 02 的实现变更须在后续实施阶段获得独立授权。

### 1.3 明确排除

-   实时行情、券商行情适配、订单执行、账户与风险引擎。
-   新交易策略、策略绩效优化或任何盈利性结论。
-   在 Phase 0 中修改代码、运行 Stage 02、重建数据产物或清理现有证据。
-   未经独立评审即修改现有 14 个 Acceptance ID
    的定义、编号或既有通过记录。
-   在证据不足时将数据质量信号直接判为错误，或为了通过门禁临时设定数值阈值。

## 2. 已核实事实与待核验事项

本节用于区分现有观察与未来决策，避免将推断写成事实。

### 2.1 已核实的当前实现事实

1.  HistData ASCII M1 文件的时间格式为
    `YYYYMMDD HHMMSS`，字段包含时间戳、OHLC 与 volume。
2.  HistData 官方规格将时间语义定义为固定
    EST（UTC−5），且不应用夏令时调整。该定义不同于会随夏令时变化的
    `America/New_York` 民用时间。
3.  Stage 01 当前把时间戳解析为 naive datetime；现有 G03 检查要求
    `ts.dt.tz is None`。现有 M1 Parquet 时间戳也表现为不携带 UTC
    调整语义的时间戳。
4.  Stage 01 的现有验收契约与 Stage D 计划中的"规范
    UTC"目标并不等价。naive 时间戳不能仅凭字段格式或变量名称被解释为
    UTC。
5.  Stage 02 当前从 M1 Parquet 读取数据，按 `df["ts"].dt.normalize()`
    形成日历日分组，并聚合：
    -   `open = first`
    -   `high = max`
    -   `low = min`
    -   `close = last`
    -   `volume = sum`
    -   `bars = size`
6.  因为 Stage 02 使用尚未转换的 naive 时间戳切日，当前 D1
    日期归属是源时间戳的日历日，不是按 UTC 00:00 切日。
7.  Stage 02 的 spike 检测实现采用 close 相对前后邻居偏离均超过 10%
    的规则，并将被隔离的 M1 行写入独立 JSONL 文件（仅当检测到 spike
    时写出）。
8.  `_g11_common.py` 中存在富 spike 证据字段契约，包括
    `reason`、`threshold`、邻居偏离度及邻居价格；当前 Stage 02
    写出结构没有完整输出这些字段，形成契约与实现漂移。
9.  `quality_contract.yaml` 对 K01 的正式定义是
    `streaming_stats_cli`：检查 Script 02 在处理文件时按文件向 stdout
    输出 JSON Lines，最低事件数为每文件 2 个。K01 不定义 spike
    quarantine。
10. `_g11_common.py` 的 docstring 提及的 `self_detect_spikes` 与
    `independent_detect_spikes`
    函数，在本次报告所述的全仓搜索中未找到；此项登记为文档债务，尚不在本阶段修复。
11. 已报告的 Stage 02 派生产物位于
    `artifacts/histdata_v9/derived/`，包括 D1 Parquet、EDA JSON 与 spike
    JSONL。此前关于"Stage 02 从未运行"的说法已被更正。
12. 现有测试没有覆盖固定 EST→UTC 转换、跨午夜日期变化或 UTC
    日线聚合；也没有 Stage 02 专属测试文件。当前 tz-aware
    拒绝测试不是转换测试。

### 2.2 已观察、但不能直接判错的质量信号

已报告的 EDA 观察包括：

-   D1 `date_min` 为 `2000-05-30`，因此"2000
    年数据"并不意味着覆盖完整自然年。
-   最大日历日期间隔报告为 11
    天，需判断其属于市场休市、源数据边界还是数据缺失。
-   有 11 个带 bar 的周六日期，需按固定 EST
    时间语义、周末会话边界和源文件记录核验。
-   首根 bar 时间存在多个常见值（例如 00:00 与
    17:00），可能反映不同会话位置。
-   HistData ASCII volume 全零；该字段不能被当作真实成交量使用。
-   最少 bars/day 为 1；必须区分残日、部分覆盖日与异常不完整日。

这些观察只作为 D-G01/D-G02/D-G03
的调查输入。不得仅凭日历间隔、星期几或单日 bar 数量就判定数据错误。

### 2.3 待评审的设计事项

-   规范 UTC 时间语义、转换方向与公式、跨午夜处理及转换结果验证要求属于 Phase 0 设计事项；规范 UTC 时间戳的物理表示方式及其与现有 Parquet/Acceptance Contract 的具体兼容实现属于实施阶段决策，须在相关实现开始前确定并记录。
-   UTC D1 与交易会话 D1 的独立 profile 定义。
-   统一 spike 证据记录字段及其校验方式。
-   PC-5 各项质量阈值的证据依据、计算方法和审批人。
-   Stage D 新契约的版本命名、证据目录结构与回滚规则。

## 3. 时间语义与日期归属

### 3.1 四层时间模型

**第 1 层：原始源时间（Source EST）**

-   保留源文件原始时间字符串和源文件定位信息。
-   对 HistData ASCII，按固定 EST（UTC−5、无 DST 调整）解释。
-   原始层不得被转换后的时间覆盖。
-   每条规范化记录必须能回溯到 `source_file` 与
    `source_line`，并能关联原始时间值。

**第 2 层：规范 UTC 时间（Canonical UTC）**

-   对经过来源识别的 HistData 时间戳，按固定偏移转换：`UTC = source EST + 5 hours`。
-   转换必须是显式、确定且可审计的；禁止把 naive 时间戳直接标记为 UTC。
-   转换证据至少记录：原始时间戳、源时区标识/偏移、转换后 UTC 时间戳、转换规则版本、源文件和行号。
-   规范 UTC 时间的语义与物理存储表示相互独立。Phase 0 必须明确源时间语义、转换方向、转换公式、跨午夜处理规则以及转换结果的验证方式。HistData 原始时间按固定 EST（UTC−5，不进行夏令时调整）解释；不得将其替换为 `America/New_York` 民用时间语义。
-   规范 UTC 时间可在实施阶段采用 tz-aware datetime、整数 epoch 或其他可验证的规范表示。具体物理存储表示属于实施阶段决策，不构成 Phase 0 退出条件。无论采用何种表示，均必须保留原始时间与转换后时间之间可核验的对应关系。不得仅因 G03 当前要求 naive 就将 naive 值视为 UTC。

**第 3 层：规范 UTC 日线（UTC D1）**

-   默认规范 D1 使用 UTC 00:00 至次日 UTC 00:00 的日历日分组。
-   D1 日期键必须由转换后的 UTC 时间戳计算。
-   OHLC 聚合按 UTC 时间顺序执行；volume 与 bars 的聚合规则需明确记录。
-   跨 UTC 午夜的 M1 bar 必须归属其 UTC 日期，不能沿用源 EST 日期。
-   应用转换后的时间轴重新计算 D1，不得通过对旧 EST D1
    结果简单改名来构造 UTC D1。

**第 4 层：交易会话日线（Session D1，可选独立 profile）**

-   交易会话日线是独立的数据产品，不与 UTC D1 混同。
-   每个 session profile 必须明确市场/数据源、IANA
    时区或固定偏移语义、会话开闭边界、周末规则、节假日规则和版本。
-   若 profile 使用纽约民用时间，必须遵循 `America/New_York` 的 DST
    规则；不能把它等同于 HistData 的固定 EST。
-   在 session profile 未经定义与测试前，不得将现有源 EST
    日切结果宣称为已验证的纽约会话日线。

### 3.2 跨午夜转换测试要求

新测试至少覆盖：

1.  EST 当日 23:30 转换后进入下一 UTC 自然日的情况。
2.  EST 00:00、日末时刻以及跨年边界。
3.  输入排序、重复时间戳和邻居关系在转换前后的处理规则。
4.  UTC D1 日期键来自转换后时间戳，而非源 EST 日期。
5.  同一输入、同一规则版本重复执行时，时间转换与日期归属一致。
6.  原始时间、转换后时间与来源定位信息之间可以逐条交叉核验。

以上是测试要求，不表示测试已存在或已通过。

## 4. 新旧验收契约边界

### 4.1 既有基线保护

-   保留当前 14 个 Acceptance ID、编号与原始语义。
-   不将 G03 的 naive 时间戳检查改写成 UTC 转换检查。
-   不将 K01 重新解释为 spike quarantine。
-   既有 Acceptance PASS 只说明其原始契约通过，不自动证明 Stage D 的
    UTC、重采样、证据完整性或研究准入要求通过。

本设计文档对 G03、K01 及其他既有 Acceptance Contract 的引用，仅用于描述当前实现行为及其设计约束，不构成对既有契约语义、编号、验收结果或历史记录的修改。G03 当前对 naive 时间戳的检查不等同于时区转换验证；K01 的 streaming statistics CLI 检查也不等同于 spike quarantine 验证。新时间语义与数据质量要求由独立的 Stage D D-series 契约负责验证。既有 14 个 Acceptance ID 保持不变。

### 4.2 新增 Stage D 契约

Stage D 应建立独立的 D-G01 至 D-G07 契约与证据记录。新增契约至少记录：

-   契约 ID 与版本；
-   输入数据集标识、源文件清单及内容摘要；
-   规则/转换版本；
-   检查方法与预期结果；
-   实际结果与证据路径；
-   状态、限制及失败原因。

新旧契约并存。若实现中发现无法兼容的行为，必须先记录差异、影响面和迁移方案，经过独立评审后才能决定是否引入后续版本；不得静默改变旧契约语义。

## 5. 证据与可追溯性契约

### 5.1 Spike quarantine 记录

Stage D
设计目标是让每个被隔离样本都能解释"哪条数据、为什么隔离、依据是什么"。建议统一证据字段至少包含：

  字段                           含义
  ------------------------------ ----------------------------
  `ts_source` 或等价字段         原始源时间戳
  `ts_utc`                       对应规范 UTC 时间戳
  `open/high/low/close/volume`   被隔离的原始 M1 值
  `source_file`                  输入文件定位
  `source_line`                  输入行号
  `reason`                       稳定的机器可读隔离原因
  `threshold`                    本次检测所用阈值
  `dev_prev` / `dev_next`        相对前后邻居的偏离度
  `prev_close` / `next_close`    参与判断的邻居价格
  `rule_version`                 检测规则版本
  `input_dataset_id`             输入数据集身份
  `event_id`（如需要）           唯一、可重复生成的事件标识

若当前 G11
契约中的字段名称不同，实施前应以实际定义为准进行字段映射；本设计不在此阶段修改任何写出器。

Spike quarantine 的可审计性同时覆盖检测命中和检测未命中两种情况。对于检测命中的记录，应能够通过来源文件和行号回溯原始数据，并提供足以复核检测判断的证据，包括适用的检测原因、阈值、邻近价格、偏离度以及隔离前后的数据量关系。最终字段定义应在实施前与现有 spike 证据契约核对，不能仅以文件存在或异常记录数量作为审计通过依据。

对于检测未命中的情况，必须能够验证检测流程已执行且未命中；不得将"没有 spike 文件"直接解释为"已执行且无异常"。空结果文件、执行摘要或其他可验证证据的具体实现方式属于实施阶段决策，但相应证据要求必须在实施前明确。

本节所列字段与命中/未命中要求构成 **D-G05 的最低证据要求（P0 必决）**，其逐条确认见 §6.2.2 与 §10.2 P0-10；其中字段名称与现有契约的映射、最终 schema、兼容策略与 `event_id` 取舍属 PRE-IMPL 必决（§10.2 PI-02）。

### 5.2 Spike 检测与准入阈值分离

-   当前 10% 规则登记为"既有实现事实"，不是已经批准的通用质量阈值。
-   **检测阈值**决定某条 M1 是否被识别并隔离。
-   **准入阈值**决定整个数据集是否可通过特定质量门禁。
-   两者必须分开配置、分别说明依据，并分别记录版本。
-   不得因为当前检测器使用 10%，就将 10% 自动设为 D-G02 的 PASS/FAIL
    标准。

### 5.3 产物来源链

D1 Parquet、EDA JSON、spike JSONL 与验证报告应能关联到：

-   输入文件清单及摘要；
-   解析产物版本；
-   规范化与聚合规则版本；
-   代码/工具版本；
-   运行参数与必要的环境信息；
-   生成时间；
-   产物自身的内容摘要；
-   任何被隔离、被排除或被警告的数据量及原因。

当前 EDA 行数与 M1
行数的对应关系可登记为内容一致性旁证；它不能替代逐字节复现性测试。

**报告类证据的命名与版本关联：** 缺口分类报告、逐日差异报告、D1 profile、用途矩阵与数据集声明适用同一来源链要求，并采用统一的命名与版本关联规则：文件名或记录标识须包含证据类型、`input_dataset_id`、规则版本与生成时间（UTC）。具体路径与命名模板属 PRE-IMPL 必决（§10.2 PI-07）；在模板确定前，不得按未定义的命名固化或引用证据。

## 6. 质量门禁 D-G01 至 D-G07

### 6.1 通用状态

-   **PASS**：强制检查全部满足，所需证据充分，且不存在未解决的阻塞问题。
-   **PASS WITH WARNINGS（PASS-W）**：强制检查均满足；仅存在已披露、已记录且经授权评审接受的限制，并有证据表明这些限制不影响当前声明的用途。
-   **FAIL**：违反强制规则、发现不可接受的数据或契约问题，或者关键证据缺失导致无法证明符合要求。
-   **NOT ASSESSED**：尚无充分证据作出判断，或必需的判定规则尚未获得批准。因证据不足与因必需规则尚未获批而保持 NOT ASSESSED 的两种情况，须在记录中分别标注成因，不得合并表述。

PC-5 数值待定不能自动转化为 PASS 或 PASS-W。若某项尚未批准的规则是下游研究准入的必要条件，相应门禁应保持 NOT ASSESSED 或按适用规则判为 FAIL；在该条件解决前，不得据此宣告相关准入已通过。所有 PASS-W 均须记录限制内容、影响范围、证据依据、接受责任和后续处理条件。不得为消除警告而无依据地放宽质量标准。

**"所需证据充分"的判定（可执行判据）：** 证据充分当且仅当以下四项同时成立：(1) 该门禁在 §6.2.2 列出的必需证据项全部具备；(2) 每项证据可定位到明确来源，即路径或记录标识、规则版本与生成方式；(3) 证据与该门禁的强制检查项逐一对应，不存在仅被"文件存在"或"脚本成功退出"覆盖的检查项；(4) 不存在未解释的差异。任一项缺失时不得判 PASS，应保持 NOT ASSESSED，或按已枚举的硬性规则判 FAIL。

**状态作出权与绑定对象：** 门禁状态只能由门禁评审人（GA，见 §7 角色表）审核后作出；规则审批人不得自行判定其规则对应门禁的状态（映射见 §6.6）。每个门禁状态绑定到具体的数据集版本、规则版本与证据版本三者，任一变更即视为既有状态失效，须按 §6.3.1 重新评估。GA 尚未任命时，相关门禁保持 NOT ASSESSED。

### 6.2 门禁定义

门禁定义由三部分组成：§6.2.1 门禁概览（检查目的、最低证据要求、失败条件与未冻结事项归属）、§6.2.2 各门禁必需 PASS 条件与硬性规则、§6.2.3 判定优先级与 §6.5 的关系。

#### 6.2.1 门禁概览

#### 6.2.2 各门禁必需 PASS 条件与硬性规则

本节列出各门禁的**必需 PASS 条件**（强制检查项）与**硬性规则**（可作为 FAIL 判据的规则清单）。本清单仅由现有 §3、§5.1、§6.5 与 §7.x 已表达的要求归纳而成，不新增要求。标注"待批准"的规则在获得批准前不得用作 FAIL 判据，且相应门禁保持 NOT ASSESSED。

**D-G01 输入完整性**

-   必需 PASS 条件（强制检查）：(1) 审计范围与"必需输入"清单已枚举并获批准；(2) 每个必需输入可读取；(3) 每文件的摘要、首末时间、行数与错误统计均已产出；(4) 实际覆盖区间与已批准范围说明一致，或差异已按已批准的分类原则归类并披露。
-   硬性规则（FAIL 判据）：必需输入缺失；必需输入不可读取；审计范围本身未经批准；覆盖缺口未分类或未披露。
-   待批准项：审计范围与"必需输入"清单的枚举、缺口分类原则（P0，见 §10.2 P0-04）；覆盖率与允许缺失范围的数值阈值（PRE-IMPL，见 §10.2 PI-06）。

**D-G02 结构与价格质量**

-   必需 PASS 条件（强制检查）：(1) 字段与已批准 Schema 一致（见 §10.2 P0-15）；(2) OHLC 关系成立（`high ≥ max(open, close)`、`low ≤ min(open, close)`、`high ≥ low`）；(3) 价格为正，非正价格已隔离且理由可追溯；(4) 被隔离样本数量在已批准准入范围内；(5) 硬性结构规则清单与异常分类原则已获批准。
-   硬性规则（FAIL 判据）：上述第 (1)(2)(3) 项任一不成立；异常样本无法追溯到源文件与行号；异常未按已批准规则处理。第 (1)(2)(3) 项所依据的硬性结构规则清单须经 DQA 批准后方可作为正式 FAIL 判据。
-   待批准项：硬性结构规则清单的枚举与批准、异常分类原则、状态判定原则及阈值批准流程（P0，见 §10.2 P0-05）；价格异常准入数值阈值（PRE-IMPL，见 §10.2 PI-05）。

**D-G03 时间与连续性**

-   必需 PASS 条件（强制检查）：(1) 时间语义已获批准并按固定 EST→UTC 转换；(2) 转换证据完整（原始时间、源偏移、UTC 时间、规则版本、源文件、行号）；(3) 时间戳顺序与重复时间戳的处理规则已获批准且一致执行；(4) 缺口已按已批准分类原则归类；(5) 跨午夜归属与已批准规则一致。
-   硬性规则（FAIL 判据）：时间语义未验证或与已批准规则不一致；转换证据缺失；缺口未分类；跨午夜归属与已批准规则不一致；重复时间戳未按已批准规则处理。
-   待批准项：时间语义与转换规则、重复时间戳与排序处理规则、缺口分类原则、源文件边界与残日分类规则（P0，见 §10.2 P0-01、P0-03、P0-06）；最大允许缺口、覆盖率及残日准入数值阈值（PRE-IMPL，见 §10.2 PI-06）。

**D-G04 重采样正确性**

-   必需 PASS 条件（强制检查）：(1) D1 日期键由转换后 UTC 时间戳计算；(2) OHLC、bars 与排除样本处理同独立对照一致；(3) 逐日差异报告已产出；(4) 独立验证满足 §7.5 的最低设计要求；(5) 浮点比较容差的原因与误差界限已获批准。
-   硬性规则（FAIL 判据）：日期归属不一致；聚合规则被违反；缺少独立于被测实现的对照证据。
-   待批准项：独立验证的最低设计要求（P0，见 §10.2 P0-07，唯一归属 §7.5）；浮点容差与具体独立实现、参考数据、测试工具（PRE-IMPL / DEFER，见 §10.2 PI-04、DF-03）。

**D-G05 隔离证据完整性**

-   必需 PASS 条件（强制检查）：(1) §5.1 所列最低证据字段齐备且可核验；(2) 命中记录可回溯到源文件与行号；(3) 未命中时具备可验证的"已执行且未命中"证据；(4) 隔离前后数量关系已记录。
-   硬性规则（FAIL 判据）：必需证据无法回溯；无法验证检测是否已执行；已知异常未按已批准规则处理。
-   待批准项：§5.1 最低证据要求的逐条确认（P0，见 §10.2 P0-10）；最终 schema、字段映射、兼容策略、`event_id` 取舍与空结果证据实现方式（PRE-IMPL，见 §10.2 PI-02）。

**D-G06 可复现性与溯源**

-   必需 PASS 条件（强制检查）：(1) 字节级与语义级复现性定义及判定边界已获批准；(2) 按 §7.6 产物级比较对象清单逐产物比较；(3) 输入、规则与代码版本可追溯；(4) 元数据与规范化规则事先确定并留存版本记录；(5) 字节级与语义级结果分别报告。
-   硬性规则（FAIL 判据）：语义级复现不成立；输入、规则或代码版本不可追溯；比较对象或元数据规则未事先确定。
-   待批准项：字节级/语义级复现定义、比较对象清单、元数据处理原则与判定边界（P0，见 §10.2 P0-08，唯一归属 §7.6）；具体 hash 算法、序列化实现与工具（DEFER，见 §10.2 DF-05）。

**D-G07 下游研究准入**

-   必需 PASS 条件（强制检查）：(1) 该用途的准入矩阵已由 DAA 批准；(2) §7.7 定义的必需门禁组合全部"已通过"；(3) 限制已充分披露；(4) 用途准入状态已按 §7.7 的合成规则导出。
-   硬性规则（FAIL 判据）：必需门禁未通过；限制未充分披露；该用途未经 DAA 批准。
-   待批准项：按研究用途划分的准入矩阵与最低门禁组合（P0，见 §10.2 P0-09）；用途矩阵的版本化载体与审批记录格式（DEFER，见 §10.2 DF-04）。

#### 6.2.3 判定优先级与 §6.5 的关系

1.  §6.2.2 的**硬性规则**清单与 §6.5 的**不得降级为 PASS-W 的情形**指向同一规则集，不得被解释为两套不同标准，也不得对同一证据作出不同状态判定。同一情形在两处表述不一致时，以更严格者为准。
2.  未列入 §6.2.2 且未获批准的"硬性规则"不得用作 FAIL 判据。但**"没有合法的 FAIL 判据"不等于"可以判 PASS"**：规则不足或证据不足时，一律保持 NOT ASSESSED。
3.  当某门禁的必需 PASS 条件或 §6.5 的允许警告条件本身以尚未批准的 PC-5 数值或尚未批准的规则为前提时，该项条件不成立，该门禁保持 NOT ASSESSED。允许警告条件不构成对该前置条件的替代，不得以 PASS-W 绕过未满足的前置条件。
4.  判定顺序为：先检查是否有已枚举的硬性规则被违反（是则 FAIL）；再检查必需 PASS 条件是否全部成立（否则 NOT ASSESSED）；再检查是否存在符合 §6.5 允许列的限制（是则 PASS-W）；否则 PASS。
5.  当 §6.2.2 的硬性规则清单与 §6.5 的不得降级为 PASS-W 情形在某门禁上列举存在差异（D-G02、D-G03、D-G04、D-G05 已观察到该情况）时，取并集：任一位置列为硬性规则或不得降级情形的，均视为该门禁的禁止情形。该并集规则仅用于消解表述差异，不改变规则内容；并集形成后须经 GA 核对一致，再纳入正式判定依据（见 §10.2 P0-13）。

### 6.3 状态判定与证据优先级

门禁判定应优先依据已批准的契约、规则和可追溯证据。对同一问题存在多个证据来源时，应记录证据之间的一致性与差异，不得仅选择有利于通过的结果。

-   关键证据缺失、强制规则不满足或结果违反已批准的硬性约束时，不得判定 PASS。
-   允许警告的条件必须事先定义，并有明确的用途限制和接受记录。
-   规则尚未批准、证据不足或尚未完成验证时，应如实保留未评估状态。
-   单纯存在历史产物、脚本成功退出或文件可读取，不足以单独证明数据质量、时间语义、隔离正确性或下游准入条件已经满足。

门禁状态与实施计划中的任务完成状态相互独立。某项实施任务已完成，不代表相关门禁已通过；某项设计允许延期，也不代表对应门禁已通过。

#### 6.3.1 门禁状态转换规则

-   **复审触发条件：** 以下任一事件发生即触发重评：必需规则获得批准；证据被补充、更正或替换；实现、规则或数据版本变更；数据集版本变更；L2 批准记录载体建立；GA 发现新的相关证据。因"必需规则尚未获批"而保持 NOT ASSESSED 的门禁，在对应规则获批后必须重评，不得自动继承先前状态。
-   **变更权限：** 状态变更只能由 GA 审核后作出并记录理由。规则审批人不得单独变更其规则对应门禁的状态。FAIL 的解除须由 GA 重新审核，并记录纠正证据与解除依据。
-   **绑定对象与时效：** 每个门禁状态绑定到具体的数据集版本、规则版本与证据版本；三者中任一项变更即使既有状态失效。状态结论须记录所绑定的三个版本标识。
-   **PASS-W 转 PASS：** 仅当 §6.5 所要求的"后续处理条件"全部满足，且 GA 重新审核并记录确认时，方可转为 PASS。不得因证据更新自动升格。
-   **FAIL 的纠正与重评：** FAIL 须先完成纠正并保留纠正前后证据，再由 GA 重新审核；未完成重新审核前不得转为其他状态。
-   **记录位置：** 状态结论及其绑定版本、审核人、时间与证据引用记录于 §7"记录位置"第 2 层。该载体尚未建立时，状态结论只作为待迁移草案记录，不得作为正式准入判定依据。在 L2 载体建立前的过渡期内，§6.1 所要求的 NOT ASSESSED 两成因（证据不足 / 规则未批）区分应在 §10.2 对应 P0/PRE-IMPL 项的状态评估中逐项体现，并在 §6.2.2 相应门禁的讨论中以显式语句注明，不得仅以「NOT ASSESSED」一笔带过；L2 载体建立后（PI-03），该区分迁移至 L2 记录字段。

### 6.4 未冻结事项归属原则

每项未冻结事项必须明确归属以下类别之一：

-   **P0 必决**：Phase 0 退出前必须明确。包括关键语义、状态判定原则、契约边界及足以指导测试设计的定义。
-   **PRE-IMPL 必决**：代码或流水线实施前必须解决，但不要求在 Phase 0 确定具体实现方案。
-   **DEFER**：允许延期处理的非阻塞实施细节；须记录责任、适用范围及必要的后续处理条件。

各门禁应分别分类，不要求所有事项一律在 Phase 0 冻结，也不允许将关键设计缺口无条件延期。分类结果应进入 Phase 0 退出检查清单，并汇总至 §10.2 的 P0 / PRE-IMPL / DEFER 总表；两者逐项对应，§10.2 为待决事项的唯一总表。若某项延期会阻止必要门禁通过，则相应门禁保持未评估或阻塞状态。

### 6.5 门禁级警告条件（PASS WITH WARNINGS）

§6.1 定义 PASS WITH WARNINGS 状态，§6.3 要求允许警告的条件必须事先定义。本节按门禁明确：哪些情形允许判为 PASS-W，以及哪些情形不得降级为 PASS-W。§6.1 与 §6.3 的通则不替代本节的门禁级规则；评审者不得自行放宽，也不得对同一证据作出不同状态判定。本节的"不得降级为 PASS-W"列与 §6.2.2 的硬性规则清单指向同一规则集，其对应关系见 §6.2.3。

| 门禁 | 允许判为 PASS-W 的情形 | 不得降级为 PASS-W 的情形 |
|---|---|---|
| D-G01 输入完整性 | 必需输入均可读取，覆盖缺口已分类且已披露，并有证据表明该缺口不影响所声明的用途 | 必需输入缺失或不可读取；覆盖缺口未分类或未披露；审计范围本身未经批准 |
| D-G02 结构与价格质量 | 硬性结构规则全部满足；被隔离样本可按已批准规则追溯且数量在已批准范围内；仅存在已披露的极端市场变化 | OHLC 关系不成立；非正价格未隔离；异常不可追溯；硬性结构规则尚未枚举或未获批准 |
| D-G03 时间与连续性 | 时间语义与转换证据完整；缺口已分类为预期休市或源文件边界；仅存在已披露的个别待解释残日 | 时间语义未验证；转换证据缺失；缺口未分类；跨午夜归属与已批准规则不一致 |
| D-G04 重采样正确性 | 日期归属与 OHLC 聚合同独立对照一致；仅浮点字段在已批准误差界限内存在已披露差异 | 日期归属不一致；聚合规则被违反；缺少独立于被测实现的对照证据；误差界限未获批准 |
| D-G05 隔离证据完整性 | 命中与未命中证据均可核验；仅最终 schema 与写出器的映射尚未完成且已披露 | 隔离记录无法回溯到源文件与行号；无法验证检测是否已执行；最低证据字段缺失且未披露 |
| D-G06 可复现性与溯源 | 语义级复现成立、字节级不成立，且字节差异已逐项归因并披露 | 语义级复现不成立；输入、规则或代码版本不可追溯；比较对象或元数据规则未事先确定 |
| D-G07 下游研究准入 | 所声明用途所需的门禁组合均已通过；仅存在已披露且与该用途无关的限制 | 必要门禁未通过；限制未充分披露；该用途未经数据集准入审批人批准 |

对所有门禁统一适用的约束：

- **NOT ASSESSED 不得因"阈值待定"自动升格为 PASS-W。** 若某门禁是所声明用途的硬性必要条件，其 NOT ASSESSED 视为阻塞。
- 每个 PASS-W 必须记录：限制内容、影响范围、支持证据、接受责任、适用的研究用途以及后续处理条件。
- PC-5 数值尚未批准时，相应门禁保持 NOT ASSESSED，不得以 PASS-W 代替。
- 不得为消除警告而在无依据的情况下放宽阈值、缩减比较范围或事后调整证据。
- **允许警告条件不得替代未满足的前置条件。** 当"允许判为 PASS-W 的情形"本身以尚未批准的 PC-5 数值或尚未批准的规则为前提时，该项条件不成立，对应门禁保持 NOT ASSESSED。

## 7. PC-5：数值阈值依据与决策方法清单

本阶段冻结质量判定的决策方法、依据类型、审批责任和记录位置，不冻结 PC-5 的具体数值阈值。每项质量规则必须说明检查对象、证据来源、判定方法、依据类型、审批责任、记录位置，以及数值尚未批准时对门禁状态的影响。具体数值应在实施前按项审批，并保留审批记录。任何阈值在获批前均属于待定项，不得作为正式准入标准。

每项规则的编号为 `PC-5-01` 至 `PC-5-07`，依次对应 §7.1 至 §7.7。该编号与 §6.6 的规则—门禁映射表共同构成规则的唯一定位方式；引用规则时应使用规则 ID，而非仅用子节号。

每项规则还应记录以下信息：

-   **规则标识：** 规则 ID（`PC-5-0x`）、当前版本号与首次生效时间。规则内容变更时必须递增版本号并保留变更留痕，不得原地覆盖而无记录。
-   **依据类型：** 用于制定规则的证据类型及其适用范围。
-   **审批责任：** 负责批准规则的角色或授权方；该角色须已在角色表中登记持有人（见下）。
-   **记录位置：** 批准规则、理由、版本及生效范围的保存位置。
-   **待定影响：** 数值未获批准时哪些门禁不能判定通过。本项须使用显式状态表述（"对应门禁保持 NOT ASSESSED"），不得只写禁止性表述。

**审批角色与权威范围（本阶段命名，属 P0 必决）：**

**角色任职、变更与授权依据（P0 必决）：**

-   角色的**任命、登记、变更与撤销**必须由项目授权主体作出，并以书面任命记录为准。项目授权主体（其具体身份由项目治理决定，本设计不指定具体个人或组织）须在任命记录中登记：被任命角色、持有人身份、任命依据、生效时间与授权范围。
-   **登记的唯一权威位置为本节角色表的"持有人"列。** 该列是判断某角色是否已指定的唯一判据；其他位置（包括后续建立的批准记录载体）只能引用或同步展示，不得作为登记源。
-   未登记持有人的角色视为**尚未指定**：其对应规则不生效，且按 §6.6 映射对应的门禁保持 NOT ASSESSED。
-   角色变更或撤销须重新登记并保留原任命记录，不得覆盖既有任命记录。
-   同一自然人可否担任多个角色，按下方"职责分离"判定；未被禁止的组合可以兼任，但须在任命记录中显式登记。

**职责分离（P0 必决）：**

本设计中的角色分为三类：**规则审批人**（DQA、TSA、CA、RSA、RPA、DAA）、**门禁评审人**（GA）、**独立复核人**（IR）。实施阶段的代码与流水线实现审批人由实施阶段另行定义，不属本节角色表。

-   GA 不得兼任其所评审门禁对应规则的审批人（映射见 §6.6）。规则制定者不得自行判定其规则对应门禁的合规状态。
-   IR 不得由 RSA 兼任，也不得由被复核实现的提供方或其批准角色兼任。
-   RSA 不得兼任所提交重采样实现的批准角色。
-   DAA 不得由被批准用途所依赖门禁的规则审批人兼任（不设"仅由"例外）。
-   角色持有人尚未登记时，相应门禁保持 NOT ASSESSED；不得以临时安排代替登记。

**记录位置（统一，属 P0 必决）：**

1. **规则决策记录（L1）：** 本文档 §7.x 各子节，记录规则内容、规则 ID 与版本、依据类型、审批角色与决策理由；本节角色表的"持有人"列记录角色登记状态。L1 是规则内容与角色指定状态的权威来源。
2. **批准记录（L2）：** 批准结论、批准角色持有人、规则版本、生效时间与生效范围。其运营载体为 Stage D 自有的版本化契约与证据记录（见 §4.2）；**不得写入既有 `artifacts/histdata_v9/quality_contract.yaml` 的既有条目**（见 §4.1）。该载体的具体路径与格式须在实施前确定并按 §10.2 记录，属 PRE-IMPL 必决。**该载体当前尚未建立，不得被描述为已存在，也不得作为角色持有人登记的依据**；L2 只引用或同步 L1 的登记结果。
3. **生效条件：** 规则生效需同时满足：对应角色持有人已在 L1 登记，且批准结论已记录于 L2。L2 载体建立之前，规则不得作为正式准入判定依据，相关门禁保持 NOT ASSESSED。此情形不阻止 §11.4 对"角色持有人已登记"的核验，因为该核验的判据是 L1 的登记状态。

任何"由项目维护者指定"而未在 L1 登记的表述，均不构成角色已指定。

例如，价格异常规则可考虑使用原始 M1 OHLC 分布、相邻价格偏离度分布和已知历史异常案例作为依据。这些属于候选证据类型，不代表具体阈值已获批准。

### 7.1 价格异常（PC-5-01）

-   **核验方法：** 检查 OHLC
    合法性、非正价格、邻居价格跳变、异常样本聚集与已知历史 glitch。
-   **证据来源：** 原始 M1、解析错误 JSONL、spike
    记录、源文件行号、独立计算的邻居偏离度。
-   **决策方法：**
    区分硬性结构错误、可隔离价格异常与仅需警告的极端市场变化；检测规则和数据集准入规则分开审批。
-   **数值：** 待定。现有 10% 规则仅作为既有实现事实。

**"极端市场变化"的可执行分类要求（判据框架属 P0，数值待批准）：** 某异常样本申明为"仅需警告的极端市场变化"时，必须同时满足：(1) 落入已批准的极端变化类别清单；(2) 具备独立于检测实现的第二证据来源（例如已知历史事件、另一数据源或独立计算的市场统计），不得仅以检测器自身的判断为据；(3) 已按 §5.2 说明其不影响本门禁的准入判定；(4) 经 DQA 批准并登记。上述第 (1) 项的类别清单及任何数值界限均为待批准项；未获批时不得以该分类宣告门禁通过。

-   **依据类型：** 原始 M1 OHLC 分布、解析错误、邻居价格偏离度、已知历史异常案例及独立复核结果。
-   **审批责任：** 数据质量审批人（DQA，见本节角色表）；具体数值阈值须单独批准，并在批准记录中登记角色持有人。
-   **记录位置：** 见本节"记录位置"第 1、2 层。规则决策记录即本子节；批准记录位于 Stage D 批准记录载体。
-   **待定影响：** 硬性结构规则清单、异常分类原则或数值阈值未获批准时，**对应门禁（D-G02）保持 NOT ASSESSED**；不得据此宣告价格质量门禁通过。

### 7.2 时间缺口分类（PC-5-02）

-   **核验方法：**
    将观测间隔与源时区、周末交易会话、节假日、文件边界和源文件覆盖范围交叉核对。
-   **证据来源：** 原始时间戳、转换后 UTC
    时间戳、按文件的首末时间、日期差分与会话日历。
-   **决策方法：**
    先分类为预期休市、数据源边界、待解释或确认缺失，再决定警告/失败；不得仅以连续日历天数判断。
-   **数值：** 待定。11 天日历缺口目前只是待调查案例。

**缺口分类的证据要求：** 每条观测缺口必须归入四类之一（预期休市、数据源边界、待解释、确认缺失），并附源文件或会话日历依据；归类为"待解释"时必须记录待解释原因、影响范围与后续处理条件。

-   **依据类型：** 原始及规范 UTC 时间戳、源文件首末范围、会话日历、周末与节假日信息、文件边界及缺口案例复核。
-   **审批责任：** 时间语义审批人（TSA，见本节角色表）；具体数值阈值须单独批准，并在批准记录中登记角色持有人。
-   **记录位置：** 见本节"记录位置"第 1、2 层。规则决策记录即本子节；缺口分类报告作为关联证据。
-   **待定影响：** 缺口分类原则未确定时，**对应门禁（D-G03）保持 NOT ASSESSED**；具体数值阈值未获批准时，不得将其作为正式准入标准。

### 7.3 覆盖率（PC-5-03）

-   **核验方法：** 对照声明的覆盖区间、实际文件
    inventory、每文件时间范围和预期会话覆盖。
-   **证据来源：**
    文件清单、内容摘要、`parse_stats.json`、错误记录、源数据规格。
-   **决策方法：**
    自然年覆盖、文件声明覆盖和有效交易时段覆盖应分别报告；文件名中的年份不等于完整年份覆盖。
-   **数值：** 待定。2000 年从 5 月 30
    日开始的事实应显式呈现，不能被"2000--2026"标签掩盖。

**覆盖缺口的可执行判定要求：** (1) 每条缺口必须归入 §7.2 的四类之一并附依据；(2) 判定"缺口不影响所声明的用途"必须以 §7.7 已批准的用途声明为前提，即用途声明已按 §7.7 的必含内容提交并处于已批准状态，且该缺口不影响该用途必需门禁组合中的任一必需项；(3) 用途声明不存在或未获批准时，不得作出"缺口不影响用途"的判定。

-   **依据类型：** 输入文件清单及摘要、文件首末时间、解析统计、源数据规格、声明覆盖范围及有效交易时段覆盖。
-   **审批责任：** 数据覆盖审批人（CA，见本节角色表）；具体数值阈值须单独批准，并在批准记录中登记角色持有人。
-   **记录位置：** 见本节"记录位置"第 1、2 层。规则决策记录即本子节；输入 inventory 与覆盖报告作为关联证据。
-   **待定影响：** 覆盖区间、缺口分类原则未明确，或用途声明未获批准时，**对应门禁（D-G01）保持 NOT ASSESSED**；数值覆盖标准未获批准时，不得将建议值作为正式阈值。

### 7.4 日线完整度（PC-5-04）

-   **核验方法：** 统计每个 UTC 日期的 M1 bar
    数、首末时间、缺口、来源覆盖和会话边界。
-   **证据来源：** M1→D1 映射表、bars/day 分布、会话
    profile、文件首末范围。
-   **决策方法：**
    区分完整日、部分覆盖日、边界残日和待解释日；只有规则与会话证据支持时才将其判为异常。
-   **数值：** 待定。单 bar 日不能仅凭数量直接判错。

**残日与待解释日的可执行判定要求：** (1) 每个 UTC 日期须归入四类之一（完整日、部分覆盖日、边界残日、待解释日），归类须附 bars 数、首末时间、来源覆盖与会话边界依据；(2) 单 bar 日不得仅凭数量判为异常；(3) 归类为"待解释日"时必须记录待解释原因、影响范围与后续处理条件；(4) 判定所需的数值界限（例如完整日的最低 bars 数）为待批准项，未获批时不得据此宣告门禁通过。

**归属：** 本规则的残日与部分覆盖日分类归属 D-G03；其每 UTC 日 bars、首末时间与来源覆盖结论同时作为 D-G01 的输入证据，但不构成 D-G01 的第二条独立规则（见 §6.6）。

-   **依据类型：** M1→D1 映射、每个 UTC 日期的 bars 数、首末时间、日内缺口、源文件覆盖及适用会话规则。
-   **审批责任：** 数据质量审批人（DQA，见本节角色表）；日线分类规则须单独批准，并在批准记录中登记角色持有人。
-   **记录位置：** 见本节"记录位置"第 1、2 层。规则决策记录即本子节；D1 profile 与逐日完整度报告作为关联证据。
-   **待定影响：** 分类规则未明确或数值阈值未获批准时，**对应门禁（D-G03，及其作为 D-G01 输入证据的部分）保持 NOT ASSESSED**；不得直接判 PASS。

### 7.5 重采样正确性（PC-5-05）

-   **核验方法：**
    使用独立实现或独立测试路径重新聚合；核对日期归属、排序、OHLC、bars
    与排除样本处理。
-   **证据来源：**
    固定输入集、转换规则版本、逐日对照结果、跨午夜与边界测试。
-   **决策方法：**
    对确定性聚合字段定义精确比较方式；浮点字段如需容差，必须说明数值原因和误差界限。
-   **数值：** 待定。不可通过放宽比较标准掩盖日期归属或聚合错误。

独立验证必须明确被验证对象、独立性边界和比较方法。至少应说明独立性是通过不同算法或实现路径、独立参考结果，还是其他可验证方式建立。对于关键重采样逻辑，不得仅以同一实现重复运行且输出一致，作为独立正确性的充分证据。具体采用何种独立实现、参考数据或测试工具可以留到实施阶段，但独立验证的最低设计要求必须在 Phase 0 明确。

**独立验证的来源要求：** 独立参照实现或参考数据必须由与被验证实现无责任关联的来源提供，或由 IR 独立构建；不得以被验证方提供的唯一结果作为独立对照。独立性来源须在批准记录中登记，并由 IR 复核确认其独立于被测实现（§6.6 角色—门禁映射、§7 职责分离）。

**独立验证的唯一归属：** 独立验证的最低设计要求由本节唯一归属 **D-G04 重采样正确性**。§7.6 定义的复现性比较不构成独立验证的替代或充分证据；两个门禁不得重复定义，也不得相互引用形成循环。

-   **依据类型：** 固定输入集、UTC 日期归属规则、独立聚合结果、跨午夜测试、逐日差异及浮点比较依据。
-   **审批责任：** 重采样审批人（RSA，见本节角色表）；独立验证结果须由独立复核人（IR）复核，IR 不得由 RSA 兼任；浮点容差须单独批准，并在批准记录中登记角色持有人。
-   **记录位置：** 见本节"记录位置"第 1、2 层。规则决策记录即本子节；测试规格与逐日差异报告作为关联证据。
-   **待定影响：** 独立验证的最低要求和比较原则未明确时，**对应门禁（D-G04）保持 NOT ASSESSED**，不得仅凭同一实现重复运行结果一致而宣告门禁通过；具体工具可延期至实施阶段。

### 7.6 可复现性（PC-5-06）

-   **核验方法：** 固定输入、参数、代码版本和规则版本，在规定环境下重复生成并比较输出。
-   **证据来源：** 输入/输出摘要、运行日志、版本信息、重复运行报告。
-   **决策方法：** 区分字节级复现与语义级复现；若格式元数据或排序造成字节差异，必须明确解释，不能将二者混为一谈。
-   **数值：** 无独立数值阈值。本项的"数值"即为下文的产物级比较对象清单与容差规则：比较对象清单属 **P0 必决**，浮点容差属 **PRE-IMPL 必决**。

字节级复现比较指定产物的实际字节内容是否一致。若产物包含时间戳、运行 ID 或其他非确定性元数据，必须明确这些元数据是否属于比较对象。未经规范化的完整文件 hash 只能证明对应文件字节是否一致，不能单独证明业务数据语义一致。

语义级复现比较预先指定的业务数据、字段、记录范围及相关语义是否一致。比较规则必须明确字段范围、记录排序、时间语义、数值表示、缺失值处理及 Schema 版本。不得在比较结果产生后再选择字段或排除差异，以获得预期结论。

Phase 0 必须明确两种复现性的定义、比较对象、元数据处理原则和判定边界。具体 hash 算法、序列化实现、工具及代码组织属于实施阶段决策。复现证据应能关联到输入数据标识、配置版本、代码版本、运行参数及产物标识。若字节级复现不成立但语义级复现成立，应分别报告结果和原因，不得将其统一记为完全复现。

任何规范化或元数据排除规则均须事先确定并留存版本记录；不得以删除差异字段的方式事后制造复现结果。

**产物级比较对象清单（P0 必决，本阶段确定）：**

| 产物 | 语义级比较字段 | 记录排序 | 时间语义 | 允许变化的元数据 | 不可变内容 |
|---|---|---|---|---|---|
| D1 Parquet | `date`、`open`、`high`、`low`、`close`、`volume`、`bars` | 按 `date` 升序 | D1 日期键由转换后 UTC 时间戳计算（§3.1 第 3 层） | 写入器与库版本、文件创建时间、compression 与行组划分 | 上列字段值、行数、行序 |
| EDA JSON | 覆盖范围、缺口清单、星期分布、bars/day 统计、volume 统计、行数 | 数组元素按日期升序 | 同 D1 | 生成时间戳、运行 ID、工具版本字符串 | 统计值、计数、集合成员 |
| spike JSONL | §5.1 所列全部证据字段 | 按 `ts_utc` 升序；同一时间戳按 `source_line` 升序 | `ts_source` 为源 EST，`ts_utc` 为规范 UTC | 无（该产物应为完全确定） | 记录集合、字段值、记录顺序 |
| 验证报告 | 门禁状态、证据引用、限制声明 | 按门禁 ID 升序 | 同 D1 | 报告生成时间、渲染格式与排版 | 状态值、证据引用、限制内容 |

字节级比较按"排除允许变化的元数据后计算规范化摘要"执行；语义级比较按上表逐字段执行。两者结果必须分别报告，不得合并为单一结论。浮点字段的比较容差须按 §7.5 的规定声明原因与误差界限，属 PRE-IMPL 必决。上表为本阶段确定的 P0 设计规格；如需增删比较字段，须经复现性审批人批准并留存版本记录，不得在比较完成后调整。

独立验证不属本节范围：其最低设计要求由 §7.5 唯一归属 D-G04；本节的复现性比较不构成独立验证的替代。

-   **依据类型：** 输入与产物摘要、代码及规则版本、运行配置、字节级比较结果、语义级比较结果和元数据差异分析。
-   **审批责任：** 复现性审批人（RPA，见本节角色表）；产物级比较对象清单与容差规则须单独批准，并在批准记录中登记角色持有人。
-   **记录位置：** 见本节"记录位置"第 1、2 层。规则决策记录即本子节；版本化比较规则与复现报告作为关联证据。
-   **待定影响：** 字节级与语义级比较对象、元数据处理和判定边界未明确时，**对应门禁（D-G06）保持 NOT ASSESSED**，不得宣告相应复现性要求通过；具体工具可延期。

### 7.7 下游研究准入（PC-5-07）

-   **核验方法：**
    按研究用途检查时间完整性、价格质量、会话定义、成交量语义及门禁状态。
-   **证据来源：** D-G01 至 D-G06 报告、数据字典、用途声明。
-   **决策方法：** 为每类用途明确 PASS
    所需门禁、警告接受条件和禁止用途；数据集不能因"整体
    PASS"而自动适用于所有研究。
-   **数值：** 待定。HistData ASCII volume
    全零，必须明确禁止将该字段当作真实成交量；是否可用于不依赖真实成交量的研究，需根据其他门禁结果单独判断。

**用途声明的必含内容（唯一权威位置）：** 每项研究用途声明必须包含：用途名称与范围；所依赖的门禁必需组合；可接受的警告条件（若接受 PASS-W）；数据限制（时间语义、volume 语义、覆盖范围）；提出方；批准状态与批准角色。§6.5 的 D-G07 行与 §8 只引用本定义，不得另行建立口径。

**与 §8 的层级区分：** 本节定义的是**用途级声明**（针对每项研究用途，由 DAA 在批准时签字），用于构建准入矩阵与判定义务；§8 定义的是**数据集级声明**（针对整个数据集，披露时间语义、覆盖范围、volume 限制、门禁状态等基础信息）。两者对象不同：用途级声明依赖数据集级声明作为输入，但不能取代数据集级声明；数据集级声明不构成任何研究用途的「已通过」判定。本节"不得另行建立口径"的限定仅针对用途级声明，对数据集级声明的披露要求不构成冲突。

**"已通过"的定义与准入合成规则（唯一权威位置）：**

-   门禁状态为 PASS 时，计入该用途的"已通过"。
-   门禁状态为 PASS-W 时，仅当该用途的准入矩阵明文接受该警告条件，且已按 §6.5 记录全部五项内容时，计入"已通过"；否则不计入。
-   门禁状态为 NOT ASSESSED 或 FAIL 时，一律不计入。
-   用途准入状态按下述规则合成：任一必需门禁为 NOT ASSESSED、或准入矩阵未获批准 → 该用途 NOT ASSESSED；任一必需门禁为 FAIL → 该用途 FAIL；全部必需门禁为 PASS，或含被矩阵明文接受的 PASS-W 且限制已披露 → 该用途 PASS 或 PASS-W。**不得在必需门禁未满足时，仅凭摘要描述给出最终 PASS。**
-   必需门禁组合的唯一权威位置为本子节的准入矩阵；§6.6 与 §6.5 只作引用。

-   **依据类型：** D-G01 至 D-G06 的评估结果、数据字典、时间与成交量语义、已披露限制及研究用途要求。
-   **审批责任：** 数据集准入审批人（DAA，见本节角色表）；DAA 不得由被批准用途所依赖门禁的规则审批人兼任。用途矩阵与准入结论须经 DAA 批准，并在批准记录中登记角色持有人。
-   **记录位置：** 见本节"记录位置"第 1、2 层。规则决策记录即本子节；版本化用途矩阵与数据集声明作为关联证据。
-   **待定影响：** 用途对应的最低门禁组合、限制或准入矩阵未明确时，**对应门禁（D-G07）保持 NOT ASSESSED**，相关用途保持未批准状态；不得笼统宣告数据集"研究就绪"或"生产就绪"。

## 8. 下游研究准入声明

在 D-G07
获得评审通过前，不得将该数据集笼统标记为"研究就绪"或"生产就绪"。

至少需要明确：

-   时间戳是否已转换并验证为 UTC；
-   D1 是 UTC 日线还是某个有版本的交易会话日线；
-   数据覆盖起止范围与未覆盖区间；
-   spike 和解析错误的数量、处理方式及追溯证据；
-   volume 字段的真实含义与限制；
-   已通过、带警告、失败和未评估的门禁；
-   被允许与禁止的研究用途。

任何策略回测结果都必须继承数据集限制，不得把未验证的时间语义或零 volume
当作可靠市场事实。

## 9. 迁移顺序、回滚与证据保留

### 9.1 建议迁移顺序

1.  评审并冻结 Phase 0 设计与 PC-5 决策方法。
2.  为 UTC 规范化、跨午夜、D1 日期归属和 spike
    证据契约编写独立测试设计。
3.  在独立版本/路径中实现规范化与验证，不覆盖原始输入。
4.  对固定输入执行对照验证，产出可审计的差异报告。
5.  完成 D-G01 至 D-G07 的门禁评估与用途审批。
6.  只有在门禁和评审通过后，才讨论将新的规范数据集用于下游研究。

此顺序是设计建议，不构成实施授权。

### 9.2 回滚条件

出现以下任一情况，应停止发布新的规范数据集并保留全部诊断证据：

-   源时区语义或转换规则无法被独立验证；
-   跨午夜日期归属与批准规则不一致；
-   OHLC、bars 或输入输出映射出现无法解释的差异；
-   隔离记录无法回溯到源文件与行号，或缺少必要检测证据；
-   相同输入和规则不能达到批准的复现性标准；
-   关键门禁为 FAIL，或关键证据为 NOT ASSESSED；
-   发现新旧契约冲突但尚无经批准的迁移决策。

回滚只意味着停止采用新派生产物、恢复到先前已知版本并保留证据；不得删除旧产物、覆盖原始输入或清理既有审计材料。

### 9.3 版本与证据保留

-   原始输入只读保留；任何规范化结果必须是独立派生产物。
-   产物必须携带输入身份、规则版本和生成工具版本。
-   新旧产物并存时，应以显式数据集 ID 和 schema/规则版本区分。
-   不得仅凭文件修改时间认定产物内容相同；内容一致性与逐字节复现性应分别报告。
-   任何证据清理或旧产物淘汰都需要独立授权，不属于本设计的默认操作。

## 11. Phase 0 评审通过标准

Phase 0 只有在以下退出检查条件均满足，或某项被明确归类为 PRE-IMPL 必决或 DEFER、允许延期且不影响退出判定时，才能宣布设计评审通过。P0 必决事项不得以延期方式绕过退出条件；如其尚未解决，应保留未通过状态。以下为退出检查清单，不是新增 Acceptance ID。

1. **时间语义闭环：** 源 EST、规范 UTC、UTC 日线及交易会话日线的语义和边界清晰；时间转换、跨午夜处理与来源追溯要求不存在相互矛盾的定义。物理存储表示允许延期至实施阶段。
2. **新旧契约边界明确：** 现有 14 个 Acceptance ID 保持不变；新 D-series 契约负责验证新增的时间语义和数据质量要求；对 G03、K01 等既有契约的描述不构成对其修改。
3. **门禁定义完整：** D-G01 至 D-G07 均有明确的检查目标、最低证据要求、必需 PASS 条件（§6.2.2）、状态判定原则和失败条件；每个门禁同时具备门禁级允许警告条件与不得降级为 PASS-W 的情形（§6.5），且 §6.2.2 的硬性规则清单与 §6.5 的不得降级情形指向同一规则集（§6.2.3）。所有尚未批准的数值规则均已标明待定状态及其对门禁的影响；未枚举的"硬性规则"不得用作 FAIL 判据，但该情形不构成判 PASS 的依据。§6.6 的规则—门禁映射表已确认。
4. **PC-5 决策方法完整：** 每项质量规则均明确决策方法、依据类型、审批责任（含角色持有人登记状态）、记录位置及数值未批准时的处理原则；审批责任角色已在 §7 角色表中命名，并已在同一角色表的"持有人"列登记持有人（§7"记录位置"第 1 层）。门禁评审人（GA）已任命，且与规则审批人的职责分离满足 §7 的分离规则。具体数值可延期，但不得将待定阈值视为已批准标准；持有人未登记的角色不视为已指定。
5. **Spike 证据可审计：** 检测命中时能够回溯来源并复核判断；检测未命中时能够证明检测已执行且未命中。最低证据要求已在 §5.1 明确并归 P0 必决；最终 schema、字段映射与 `event_id` 取舍归 PRE-IMPL 必决（§6.2 D-G05、§10.2）。空结果的具体实现方式可以延期至实施前解决。
6. **复现性足以指导测试设计：** 字节级复现与语义级复现的定义、产物级比较对象清单（§7.6）、元数据处理原则及判定边界明确；独立验证的最低设计要求由 §7.5 唯一归属 D-G04，且不与复现性重复定义；具体工具和实现方式可以延期至实施阶段。
7. **未冻结事项均有归属：** §6.2 的门禁级未冻结事项、§6.6 的规则—门禁映射与 §10.2 的待决事项总表（P0 / PRE-IMPL / DEFER）均已分类，并明确其对相关门禁和后续工作的影响；§10.2 的三类表项与 §6.2 归属列逐项对应，§10.2 的程序性说明不参与分类。
8. **迁移、回滚与证据保护原则明确：** 设计能够说明新旧数据产物的边界、迁移顺序、回滚条件及证据保留原则；不得通过删除或覆盖历史证据来制造通过结果。
